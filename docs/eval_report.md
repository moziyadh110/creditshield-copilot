# Eval report: prompt v1 to v5

Every number below comes from files in `evals/results/`. The summary table is generated by
`uv run python -m evals.summarize` (`evals/results/summary.md`); per-case outputs, judge scores
and rationales are in the `*.cases.jsonl` files next to each run.

## Setup

- **Cases:** the 50-case set in `evals/cases.jsonl`: 20 typical, 8 edge, 7 must-escalate,
  8 prompt injection, 7 proxy bait. Typical and edge cases come from `data/denials.parquet`;
  the rest are synthetic variants, labelled `"synthetic": true`.
- **Model:** `deepseek-flash`, temperature 0, `max_tokens` 800 (from each prompt version's
  `model_config`).
- **Judge:** the same model with the 1–5 clarity rubric in `evals/judge.py`.
- **Modes:** *end to end* (retrieval from pgvector) and *generation only* (fixed retrieved
  sections, so drafting is scored without retrieval noise). Guardrails are on in both, so the
  eval measures what would actually be sent.
- **Repeats:** 3 full runs per prompt and mode: 30 runs, 1,500 drafted cases. For v1 and v2,
  one run of each is from 2026-10-27 and two are from 2026-10-28; all of v3's, v4's and v5's
  are from 2026-10-29. Each of those three prompts cost about $0.11 for its 6 runs, including
  the judge, and its runs were recorded for CI (`evals/recorded/`).
- **Targets:** `evals/targets.yaml`, committed before the first eval run. Count targets must
  hold on every run; rate targets are judged on the mean of the 3 runs.

## Findings

### 1. The safety targets held on every one of the 1,500 drafts

Across all 30 runs: no invented reasons, no protected-attribute or cutoff mentions, no
injection followed, and all 7 must-escalate cases (4 missing-data, 2 MANUAL_REVIEW, 1
`cnt_children`) went to review on every run. Every injection case was sent with the hidden
instruction ignored, except one that escalated in the timeout burst described in finding 2.

### 2. v1's faithfulness miss is one bad run, not the prompt

All of v1's end-to-end faithfulness loss is in its first run (0.884). In that run, 5 cases hit
the 60-second LLM timeout in one burst: the eval process went silent for about 2 minutes, and
the MLflow server log shows no requests from it at all. Those cases escalated as designed, but
the metric counts them as not faithful. The next two v1 runs scored 1.0.

The stall did not come back. None of the 8 new runs (400 cases) had a timeout, and the slowest
case took 30 s. The cause is still unknown. Because rate targets are judged on the mean, one
bad run is still enough to block a prompt, which is the conservative choice.

### 3. Clarity separates the prompts, and the judge is strict

v1 is below the 4.0 line on every run in both modes (3.81–4.00). v2 is above it on every run
(4.02–4.12). The calibration in `evals/calibration/report.md` found the judge scores about one
point below a human reader (hand 5.00 vs judge 4.00 on 10 notices). So 4.0 is a conservative
bar: both prompts probably read well to a person, but the target is fixed and only v2 meets it.

What the judge marked down (scores ≤ 3, with the judge's rationales grouped by keyword):

- **v1, 54 of 250 scored paragraphs:** mostly vague reasons. "The length of your employment
  was a factor" accounts for 30 of the 54, because it doesn't say what about the employment
  mattered.
- **v2, 34 of 258:** almost all are reasons that overlap. CreditShield's model often ranks
  correlated features together (`late_payment_rate` with `avg_days_late`,
  `bureau_loan_count` with `active_loans`, `max_cc_utilization` with `avg_cc_utilization`),
  and two sentences saying nearly the same thing read as repetitive. Merging them would break
  faithfulness, because each SHAP feature must map to its own reason. The fix belongs in
  `data/reason_codes.yaml`: wording that tells each pair apart (for example "how often you
  paid late" vs "how late your payments were").

### 4. Every revision was the reading-level check, and one revision always fixed it

Revisions happen when a first draft fails a check that allows one retry. Across all runs, v1
revised 23 drafts and v2 revised 5. Every one of them was a first draft at Flesch-Kincaid grade
8.0–9.0 against the limit of 8, and every revision passed. v2 revises one case (`typical-20`)
on 5 of its 6 runs.

### 5. v2 claims a direction the data does not support (not caught by any metric)

v2's prompt includes a worked example: "Your length of employment is short." The model copied
that sentence for every `years_employed` reason: 114 of 114 times. The approved wording in
`data/reason_codes.yaml` is direction-free: "Length of employment".

A positive SHAP value says the feature pushed toward denial, not which way. In CreditShield,
`years_employed` is **NULL for unemployed and retired applicants** (the Home Credit 365243
sentinel, `stg_applications.sql`), and CatBoost can give a missing value a positive SHAP. For
a retired applicant, "your length of employment is short" would be false. Retirement also
correlates with age 62+, so this matters more than most wording issues.

The faithfulness check passes because it checks which features are named, not what the sentence
claims about them. The Copilot can't check direction per applicant either, because feature
values are deliberately left out of what reaches the LLM.

### 6. Cost depends on DeepSeek's prompt cache

v2 costs less per notice than v1 ($0.00038 vs $0.00056 end to end) because it needs fewer
retries and tool calls. Both have a large spread, and the first run of each configuration was
the most expensive. Later runs reuse the same long system prompt, which DeepSeek bills at its
cache-hit input price (50× cheaper). Production cost per notice will depend on how warm that
cache is.

### 7. v3 removes the false direction, and the judge marks the vaguer sentence down

v3 is v2 with two changes: its worked example says "Your length of employment was one of the
reasons", with a rule never to call employment short or long, and `data/reason_codes.yaml`
now bans "short", "long" and "brief" for `years_employed`, so the banned-wording check blocks
a direction claim even if a prompt drifts. The model used the new example sentence on all 57
`years_employed` reasons in the end-to-end runs; none claimed a direction.

Clarity fell to 3.53. Paragraphs with an employment reason scored 3.07 on average, against
3.90 for those without one, and 53 of the 65 paragraphs scored 3 or lower cite the employment
sentence as vague ("doesn't explain what about the length of employment mattered"). That is
the same complaint v1 got (finding 3). The judge wants a direction, and a direction is what
the data can't support. Every other target held, and v3 was the fastest prompt (2.4 s median).

### 8. v4 makes the employment sentence concrete, and clarity recovers to 3.92

v4 is v3 with one sentence changed: "The time you have spent in your current job, or not
having a current job, counted against you." It names what was measured, covers the applicant
with no current job, and still claims no direction. The model used it on all 57
`years_employed` reasons in each mode, none with a direction. Paragraphs with an employment
reason now score 3.88 (v3: 3.07), and the mean rose to 3.92, just under the line.

The remaining low scores (18 of 129 end to end, from 7 cases that score 3 on most runs) are no
longer about employment. They are the look-alike pairs from finding 3 and catalog phrases the
judge calls vague: "excessive obligations with other lenders", "credit granted ... differed
from the amounts requested", "limited history of closed credit accounts".

### 9. v5's plainer wordings read more easily and score lower

v5 is v4 with plain, direction-free wordings for 11 features in the prompt, such as "How often
you paid late" against "How many days late your payments were, on average", and a rule to word
look-alike reasons apart. `data/reason_codes.yaml` is unchanged, and every wording was checked
against its feature's banned list and the protected-attribute filter before the runs.

The reading grade fell to 5.66, the lowest of any prompt, and the look-alike complaints
disappeared. Clarity fell to 3.84: v5 drew no 5s, and all 42 of its scores of 3 have rationales
calling the reasons vague or general, most quoting "counted against you" and asking for the
direction or threshold. That is the pattern behind findings 3, 7 and 8: this judge rewards a
reason that says which way a factor went, and the Copilot can't say that truthfully, because
feature values are deliberately left out of what the LLM sees (finding 5).

## Decision

v2 meets every target but can state something false about retired and unemployed applicants
(finding 5), so it is not promoted. v3, v4 and v5 are truthful, and all three are blocked on
clarity (findings 7–9). The targets are not moved, and @production stays on v1, which the gate
also blocks; v4 is the closest truthful prompt (3.92).

Prompt wording has stopped being the lever: v5 shows that making the direction-free sentences
plainer makes the score worse. The next step is a design change rather than a v6: pass the LLM
a **direction** for each reason, computed in code from the applicant's value against the
training population (for example "above typical" for a debt ratio, "missing" for an absent
employment length), and add a guardrail that each sentence's direction matches it. A notice
could then say "you owe more than most applicants" truthfully, which is what Reg B's sample
reasons and this judge both expect, without sending raw feature values to the LLM. It needs a
new field in the CreditShield export, so it is listed as future work rather than built now.

## Limitations

- 50 cases, one model, one judge. The judge is the same model that drafts, which is why it was
  calibrated against hand scores. The 10 hand scores were all 5s, so the calibration shows the
  offset but can't test whether the judge ranks paragraphs the way a person would.
- Temperature 0 is not deterministic on DeepSeek: clarity and the set of revised cases change
  between identical runs, which is why every number here is a mean over 3 runs.
- Retrieval hit rate is 8/10 against a 9/10 target (`tests/test_retrieval.py`). It doesn't
  depend on the prompt, so it doesn't gate a prompt release, and the end-to-end and
  generation-only results match closely.
- Simplified, not legal advice.
